# 問題データの生成

`content/<theme>/<category>.json` の知識カードと問題を作る。質がこのアプリの肝なので、**量より正確さと分かりやすさ**を優先する。

## 最初に必ず読むもの

1. `docs/content-guide.md` — 執筆ガイド。すべての基準はここに従う
2. `docs/adr/0008-question-formats-and-data-model.md` — 出題形式とデータ構造
3. `src/schema.ts` — スキーマの正本
4. 対象テーマの `content/<theme>/_theme.json` と、対象サブカテゴリの既存ファイル（あれば）
5. ほかのサブカテゴリの知識カードの ID とタイトル（`links` の候補にする。`pnpm review` の出力か JSON を見る）

## 進め方

### 1. 構成案を作り、ユーザーの確認を取る

いきなり JSON を書かない。まず次の表を示して合意を取る（ユーザーが「おまかせ」と言った場合を除く）。

- サブカテゴリを貫く問い（新しいサブカテゴリの場合）
- 知識カードの一覧: タイトル・年・`why` の要点・解放順
- 問題の一覧: 形式・問うこと・対象の知識カード
  - 形式は内容で選ぶ（年代の前後 → 並べ替え、宗派と開祖 → 組み合わせ、場所 → 地図 など）
  - 知識カード 1 枚につき問題 3 問程度（「何・誰」「いつ・どこ」「なぜ」）を目安にし、表に各問題の `asks` を書く
  - `why` のある知識カードには「なぜ」を問う問題を必ず作る
  - サブカテゴリの問いに答えるうえで抜けている時代・出来事がないかも確認し、あれば知識カードの追加を提案する
  - 1 回の生成は知識カード 15 枚・問題 20 問を目安にする（それを超える場合はユーザーに伝える）

### 2. 事実を確認する

知識カードごとに、書く内容（年・人物・場所・なぜ・へぇ）を資料で確かめる。

- 資料の優先順位: 公的機関・博物館・美術館・寺社の公式解説 > 百科事典（コトバンクの日本大百科全書・世界大百科事典など） > Wikipedia（ほかの資料の確認の手がかりとして使う）
- `WebFetch` で読む（この環境ではシェルからの外部接続はできない）。1 枚につき少なくとも 1 つ、学説の状況（意図か結果か、定説か異説か）を書く場合は 2 つ以上の資料で確認する
- **2 つ目の資料は Codex で探す。** Wikipedia 以外の資料が見つからない記述（特に学説の状況・「なぜ」）は、Codex の Web 検索に資料を探させる
  ```bash
  codex --search exec -m gpt-5.6-luna --skip-git-repo-check -s read-only -o "$TMPDIR/codex-research.md" "<確認したい記述を番号付きで列挙し、Wikipedia 以外の資料（コトバンク掲載の百科事典、公的機関・博物館・寺社・大学のページ）で、判定（支持／一部支持／支持されない／確認できず）・根拠の要約・資料名と URL を答えるよう依頼する>"
  ```
  - 数分かかるので、確認したい記述はまとめて 1 回で依頼する
  - **Codex の回答をそのまま出典にしない。** 挙がった URL を自分で `WebFetch`（PDF は保存先を `Read`）で開き、書かれている内容を確かめたものだけを `sources` に入れる。開けなかった・読めなかった資料は使わない
  - 「一部支持」とされた記述は、根拠に合わせて書き直す
- 資料どうしが食い違う・確認できない内容は、ガイドの「確からしさの表現」に従って書き分けるか、書かない
- 確認した内容を `content/<theme>/<category>.notes.md` に記録する（下の書式）。コミットして、あとから何を確かめたかを追えるようにする

### 3. JSON を書く

- ID の付け方（一度付けたら変えない）
  - 知識カード: `<テーマ略号>-<サブカテゴリ>-<内容>`（例: `jh-religion-buddhism-arrival`）。テーマ略号は既存に合わせる（日本史 `jh`、絵画 `pt`）
  - 問題: `q-<テーマ略号>-<サブカテゴリ>-<内容>`（例: `q-jh-religion-kokubunji-purpose`）
  - 選択肢・項目: 内容を表す短い英小文字（例: `honen`、`zen`）
- `sources` には確認に使った資料を「資料名 — URL」の形で書く
- `unlockOrder` は、問いへの答えが順に見えてくる並び（多くは年代順）にする
- 新しいサブカテゴリは `_theme.json` の `categories` に `id`・`name`・`description`（貫く問い）を追加する
- 既存の問題を直すときは ID を変えない。内容が別物になる場合は新しい ID で作り、古い問題を `"status": "retired"` にする

### 4. 画像を用意する（必要な場合）

- 絵画はパブリックドメイン、写真は CC ライセンスのものだけを使う（ADR-0004）。Wikimedia Commons の API（`action=query&prop=imageinfo&iiprop=url|extmetadata`）を `WebFetch` で読み、ファイル名・作者・ライセンスを確かめる
- 取得したい画像を `scripts/fetch-images.ts` の一覧に追加し、`credit`・`license`・`sourceUrl` を media に書く
- ダウンロードはユーザーに `pnpm fetch:images` を実行してもらう（この環境からは取得できない）
- マーカー（部分指定）は、ガイドの「部分指定（マーカー）の使い方」に従う。画像がない状態では作らない。`pnpm check:markers` の画像を `Read` で見て位置を確かめ、正しいときだけ `--approve` する

### 5. 検証する

- `pnpm validate` を通す。エラーはすべて直す。問いの抜けの警告も、理由があって残す場合を除いて解消する
- `pnpm test` を通す

### 6. 自分でレビューする

学習者になったつもりで、全問を次の観点で読み直し、問題があれば直す。

- 知識カードを読んでいない人が、問題文と解説だけで理解できるか（指す対象が具体的か、用語に説明があるか、変化を問う問題に「それまで」の説明があるか）
- 問題文だけで答えが一つに決まるか。別の選択肢も正解と言える余地はないか
- 誤答は紛らわしいが明確に誤りか。議論のある内容を誤答にしていないか
- `why` は意図を書いているか（結果と混ざっていないか）
- `trivia` は基準を満たし、答えのない疑問を残さないか
- 解説は、なぜその答えになるかを説明しているか
- つながりはこじつけになっていないか
- `pnpm review` の「問いの網羅状況」で、問題が 1〜2 問しかない知識カードや「なぜ」の抜けがないか
- ガイドのチェックリストをすべて満たすか

### 7. レビュー用ページを出して報告する

- `pnpm review <theme>/<category>` で `.cache/reviews/<theme>-<category>.md` を作る（確認メモも末尾に入る）
- ユーザーへの報告に含めるもの:
  - 作った知識カード・問題の数と形式の内訳
  - レビュー用ページのパス
  - **確認しきれなかった点・資料で説が分かれた点**（隠さず列挙する）
  - ユーザーにお願いすること（`pnpm fetch:images`、実機での確認など）
- 確認メモの内容を、ユーザーへの報告で省略しない

## 確認メモの書式

```markdown
### <知識カードのタイトル>

- 確認した内容: 年（538年、552年説あり）、人物、なぜ（〜）
- 資料: 資料名 — URL
- 注意: 資料で説が分かれた点、書き分けた表現、確認できず書かなかったこと
```
