# 0008. 出題形式とデータモデル（知識カードと問題の 2 層）

- ステータス: 承認（未実装）
- 日付: 2026-09-25
- 関連: ADR-0001, ADR-0002, ADR-0003, ADR-0004, ADR-0006

## 背景

歴史・絵画・建築・社会などのテーマでは、内容によって適した問われ方が異なる（年代の前後関係、作品と作者、場所、分類など）。また 1 つの知識は複数の形で問える（「いつ？」「どこ？」「並べ替え」）。一方、つながり（ADR-0001）や年表・地図の表示は「問題」ではなく「知識」の単位で扱いたい。

## 決定

### データは「知識カード」と「問題」の 2 層に分ける

- **知識カード（item）**: 覚える対象の 1 単位（例: 島原・天草一揆）。概要・なぜ（目的・背景・原因）・年・場所・人物・画像・つながり・豆知識・出典を持つ
- **問題（question）**: 知識カードの問い方の 1 つ。1 つ以上の知識カードを参照する。複数の知識カードを参照する問題（並べ替えなど）を「まとめ問題」と呼ぶ
- 解説（なぜその答えになるか）は問題に、なぜ・つながり・豆知識は知識カードに持たせる。解答後の画面では「解説 → なぜ → つながり → へぇ」の順に表示する。なぜは、問題が参照する知識カードが 1 つのときだけ表示する（まとめ問題では情報が多くなりすぎるため）
- 各項目に何を書くか（意図と結果の区別、確からしさの表現、へぇの基準など）は `docs/content-guide.md` に定める
- 問題の解放（ADR-0002）は知識カード単位で行う。知識カードが解放されると、その知識カードだけを参照する問題が出題対象になる。まとめ問題は、参照するすべての知識カードが解放されたときに出題対象になる

### 復習と★は問題単位

- FSRS のスケジュールと★（定着度、ADR-0002）は問題ごとに持つ。まとめ問題も他の問題と同じく扱う
- 進捗表示（★の分布）・解放条件（「あと N 問を★★★」）は問題数で数える
- 知識カードの一覧では、そのカードを参照する問題の★を並べて表示する（知識カード自体は★を持たない）

### 問題が何を問うかを持つ

- 各問題は、知識カードの何を問うかを `asks`（`what` 何／`who` 誰／`when` いつ／`where` どこ／`why` なぜ／`result` 結果）で持つ
- 知識カードごとの問いの抜け（特に `why` があるのに「なぜ」を問う問題がないもの）を、検証の警告とレビュー用ページで見える化する
- 学習データ（ADR-0006）で「なぜを問う問題が苦手」のような分析にも使う

### 出題形式

文字の自由入力は使わない（スマホでの入力負担と採点の難しさのため）。MVP から以下のすべてを実装する。

| 形式 | `type` | 内容 | 採点 |
|---|---|---|---|
| 択一 | `choice` | 4 択。問題文・選択肢の両方に画像を使える | 正誤 |
| 並べ替え | `order` | 年代順・手順順などに並べる | 完全一致。部分正解数を表示 |
| 組み合わせ | `match` | 作品と作者、人物と出来事などを結ぶ | 完全一致。部分正解数を表示 |
| 分類 | `classify` | 項目を箱（例: バロック / 印象派）に振り分ける | 完全一致。部分正解数を表示 |
| 年代推定 | `year` | スライダーで年を答える | 許容幅内なら正解 |
| 地図 | `map` | 地図上の地域をタップする | 正誤 |
| 部分指定 | `choice` + マーカー | 画像に番号付きの丸（マーカー）を重ね、どれが問われた部分かを選ぶ（建築の部位、絵の中のモチーフ） | 正誤 |

- ○× 形式は単独では使わず、「誤りを含むものを選べ」の択一にする
- 部分指定は自由にタップさせず、マーカーを選択肢にした択一として扱う。マーカーの位置は多少ずれても成立するため、座標を厳密に作る必要がない
- マーカーは推測で置くと大きくずれる（サンプル作成時に実際に起きた）ため、次の仕組みでずれを防ぐ
  - 対象は大きくはっきり区別できるものに限り、3〜4 個まで・互いに離して置く（間隔は `pnpm validate` で検査）
  - 描画した画像を目で確認した記録として、「画像 + マーカー座標」のハッシュを `content/_marker-checks.json` に保存する（`pnpm check:markers --approve`）。画像の差し替えやマーカーの変更でハッシュが変わると `pnpm validate` がエラーにし、確認し直しを強制する
  - 細部を問いたい場合は、位置を問題文で説明する文字の択一にする
- テーマごとの主な形式（生成時の目安）:
  - 日本史・世界史: 択一・並べ替え・組み合わせ・年代推定・地図
  - 絵画: 画像付き択一・分類・組み合わせ・部分指定
  - 建築: 画像付き択一・分類・地図・部分指定
  - 社会（公民・地理）: 択一・分類・並べ替え
- 生成時は内容と形式の対応ルール（年代の前後関係 → 並べ替え、作品 → 画像付き択一、場所 → 地図など）に従い、形式を選ぶ

### 地図データ

| 用途 | データ | ライセンス | 時期 |
|---|---|---|---|
| 世界（現在の国境） | Natural Earth（または TopoJSON 化した world-atlas） | パブリックドメイン（world-atlas は ISC） | MVP |
| 日本（現在の都道府県） | Natural Earth（Admin 1 – States, Provinces。47 都道府県を含む） | パブリックドメイン | MVP（`pnpm build:map` で生成済み） |
| 日本（旧国・令制国） | みるラボ 令制国マップ（CODH『幕末期近世村領域データセット』が元） | CC BY-SA 4.0 | 旧国名を問いたくなった時点で追加 |

- MVP の地図問題は現在の境界だけで作り、問題文で「現在の都道府県で」「現在の国で」と明記して、歴史上の境界との曖昧さをなくす
- 地図形式（`map`）は都道府県・国の単位で問う。それより細かい地点（島原・堺など）は、白地図にマーカーを重ねた択一（部分指定と同じ仕組み）で問う
- 元データは mapshaper などで簡略化し、地域 ID を付けて `content/_maps/` に置く。出典とライセンスを同じ場所に記録し、アプリにも表示する
- 小さな地域（香川・東京など）はスマホでタップしにくいため、拡大表示または地方ごとの拡大図を用意する
- 使わないもの:
  - geolonia/japanese-prefectures（GFDL。ライセンス文の同梱などの条件が扱いにくい）
  - CODH 旧国・旧郡境界データセット（CC BY-NC。非営利に限られる）
  - historical-basemaps（GPL-3.0。作者自身が精度の確認を求めており、過去の国境の正確さに不安がある）
  - 国土数値情報 行政区域（CC BY 4.0 だが、二次利用に申請が必要な場合があるとの注記がある。都道府県単位の問題には Natural Earth の精度で足りるため使わない。市区町村単位の地図が必要になったら再検討する）

### 採点結果と FSRS 評価の対応

| 結果 | 評価 |
|---|---|
| 正解・自信あり | Good |
| 正解・迷った | Hard |
| 不正解 | Again |
| 部分正解（並べ替え・組み合わせ・分類） | Again |

### データ構造

ファイル配置は ADR-0001 のとおり `content/<theme>/_theme.json`（テーマとサブカテゴリの定義）と `content/<theme>/<category>.json`（知識カードと問題）。地図データは `content/_maps/` に置く。スキーマは zod で定義し、問題は `type` による discriminated union とする。

```ts
// content/<theme>/_theme.json
type Theme = {
  id: string; name: string
  categories: { id: string; name: string; period?: [number, number] }[]  // 配列順 = 表示順
}

// content/<theme>/<category>.json
type CategoryContent = { items: Item[]; questions: Question[] }

type Item = {
  id: string                  // 不変
  title: string
  summary: string             // 何が・いつ・どこで・誰が（1〜2 文）
  why?: string                // なぜ: 目的・背景・原因（制度や政策は意図）
  year?: { from: number; to?: number; approx?: boolean }
  place?: { name: string; region?: string }   // region は地図の地域 ID
  people?: string[]
  tags: string[]
  media?: Media[]
  links?: { axis: "時代" | "地理" | "因果" | "人物" | "比較"; text: string; itemIds: string[] }[]
  trivia?: string
  asOf?: string               // 情報の時点（統計・制度など変わりうるもの）
  sources: string[]           // 検証に使った出典
  unlockOrder: number         // サブカテゴリ内の解放順
}

type Entry = { id: string; text?: string; media?: Media }

type Question = {
  id: string                  // 不変
  itemIds: string[]
  prompt: string
  media?: Media[]
  asks: ("what" | "who" | "when" | "where" | "why" | "result")[]   // 何を問うか
  explanation: string
  status: "active" | "retired"
} & (
  | { type: "choice";   choices: Entry[]; answer: string }
  | { type: "order";    entries: Entry[]; answer: string[] }
  | { type: "match";    left: Entry[]; right: Entry[]; pairs: [string, string][] }
  | { type: "classify"; buckets: Entry[]; entries: (Entry & { bucket: string })[] }
  | { type: "year";     answer: number; tolerance: number }
  | { type: "map";      map: string; answer: string }            // map は content/_maps/ の ID、answer は地域 ID
)

type Media = {
  kind: "image" | "svg" | "mermaid"
  src: string; alt: string
  credit?: string; license?: string; sourceUrl?: string
  markers?: { id: string; label: string; x: number; y: number }[]   // 部分指定用。x, y は画像サイズに対する 0〜1 の比率
}
// 部分指定: 問題の media にマーカー付き画像を置き、choices の各 id をマーカーの id と一致させる
```

- 選択肢・項目にも ID を持たせ、表示順はアプリがシャッフルする。「よく選ばれる誤答」（ADR-0006）はこの ID で集計する
- 知識カード・問題の ID は不変とし、内容が別物になる場合は新しい ID を振って旧問題を `retired` にする（ADR-0001）

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **知識カード + 問題の 2 層（採用）** | 1 つの知識を複数の形で問える。つながり・年表・地図を知識単位で扱える | データ構造がやや複雑 |
| 問題のみの 1 層 | 単純 | 同じ知識の情報（年・場所・つながり）が問題ごとに重複する |
| ★を知識カード単位（問題の★の最小値） | カード単位の達成感が分かりやすい | まとめ問題の扱いが複雑。進捗の数え方が問題数とずれる |
| **★を問題単位（採用）** | FSRS の単位と一致し、単純 | カードの一覧では複数の★を並べる必要がある |
| MVP は択一と並べ替えのみ | 実装が軽い | 形式の多様さ（飽きさせない工夫）を MVP で検証できない |
| 自由入力の形式を含める | 記憶の想起として効果が高い | スマホで入力しにくい。表記ゆれの採点が難しい |

## 結果

- 良い影響: 内容に合った形式で出題でき、MVP の段階で形式の多様さを検証できる。つながりや年表・地図を知識単位で表示できる
- 悪い影響: MVP の実装量が増える（形式ごとの UI・採点・生成ルール）
- リスク:
  - CC BY-SA の旧国データを加工した地図データは、同じ CC BY-SA で公開する必要がある
  - マーカーの位置を LLM が誤る可能性がある → マーカーを重ねた画像を描画し、Claude が画像を見て確認して記録を残す。加えて人がレビューする
  - 部分正解を Again とするのは厳しすぎる可能性がある → 利用状況を見て調整する
