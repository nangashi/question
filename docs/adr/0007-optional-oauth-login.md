# 0007. ログインは任意とし、Google / GitHub の OAuth でログインして同期する

- ステータス: 提案
- 日付: 2026-09-25
- 関連: ADR-0003, ADR-0005, ADR-0006

## 背景

認証があると、書き込み API の不正利用の防止、端末間での進捗同期、iOS でのデータ消失の解消、他の利用者の学習データの集計（ADR-0006）が可能になる。一方で、使い始めの手間や個人データの取り扱いが増える。

## 決定

- ログインなしでも遊べるようにし、ログインは任意とする
- ログイン手段は Google（必要に応じて GitHub）の OAuth とし、Hono + D1 + better-auth で実装する
- ログインした利用者のみ、サーバーへの同期と学習データの送信を行える。書き込み API（ADR-0005）はログイン済みのセッションに限定する
- セッションは同一オリジンの Cookie で管理する（ADR-0005 により CORS は不要）
- 未ログイン時の学習記録は、初回ログイン時にまとめてサーバーへ送り、ADR-0003 の方式でマージする
- 保存する個人データは、OAuth プロバイダ上のユーザー ID のみとする。メールアドレスは保存しない。プライバシーポリシーとアカウント削除機能を用意する
- 管理用の読み取り API は、引き続き Bearer トークン（または Cloudflare Access のサービストークン）で保護する

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **OAuth（Google / GitHub、採用案）** | 一般的でスマホで使いやすい。パスワードを預からない | OAuth アプリの登録・コールバック URL の設定が必要 |
| パスキー | 指紋や顔で認証でき、パスワード不要 | 端末を紛失した際の復旧手段が別途必要 |
| マジックリンク（メール） | パスワード不要 | メール送信サービスが別途必要 |
| 引き継ぎコード（QR） | 個人情報を一切持たない | 利用者がコードを管理する必要がある。不正利用対策にならない |
| 外部認証サービス（Firebase Auth、Clerk） | 実装が手軽 | 外部依存が増える |
| ID / パスワード | 外部依存がない | 無料プランの Workers の CPU 制限（10ms）をハッシュ計算が超えやすい。パスワードを預かる責任が重い |
| ログイン必須 | 設計が単純 | 使い始めの手間が増える |

## 結果

- 良い影響: 書き込みの不正利用を防げる。端末間の同期ができる。他の利用者の学習データを品質改善に使える
- 悪い影響: 実装とテストの手間が増える（目安 1〜2 日）。未ログイン / ログイン済みの両方の状態をテストする必要がある
- リスク: 個人データの取り扱い → 保存項目を最小化し、削除機能を提供する
