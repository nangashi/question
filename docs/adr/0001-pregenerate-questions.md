# 0001. 問題は LLM で事前生成し、静的 JSON として配信する

- ステータス: 承認（未実装）
- 日付: 2026-09-25
- 関連: ADR-0002, ADR-0004, ADR-0006, ADR-0008

## 背景

「社会」「日本史」「世界史」「建築」「絵画」などのテーマごとに、LLM で問題を生成してスマホで解きたい。アプリは public 公開する可能性があるため、API キーの秘匿・コスト・不正利用・問題の正確性を考慮する必要がある。

## 決定

問題は開発者の手元（Claude Code やスクリプト）で事前に生成し、JSON としてリポジトリにコミットして静的に配信する。アプリ実行時には LLM を呼ばない。

- 問題は「テーマ > サブカテゴリ」の 2 階層で分類する（例: 日本史 > 江戸、絵画 > バロック）。階層はこれ以上深くしない。テーマとサブカテゴリの一覧（名前・並び順・年代の範囲など）はテーマごとの定義ファイルに持つ
- 問題データは `content/<theme>/<category>.json` に置き、スキーマ（zod）で検証する。問題がまだないサブカテゴリも定義ファイルには載せ、アプリで「準備中」として表示する
- 知識カード・問題は**不変の ID** を持つ。文言修正しても ID は変えず、学習記録（ADR-0003）との対応を保つ。内容が別物になる場合は新しい ID を振り、旧問題は無効化フラグで出題対象から外す
- データは知識カードと問題の 2 層で持つ。項目・出題形式・データ構造は ADR-0008 で定める。主な内容は以下
  - 解説: なぜその答えになるか。2〜3 文。必要なら紛らわしい選択肢が違う理由も書く
  - つながり（任意）: 他の知識と結びつける 1〜2 件。軸（時代・地理・因果・人物・比較）と関連する知識カードを持つ。こじつけになる場合は作らない
  - 豆知識（任意）: 意外な事実。あるときだけ 1 行で表示する
  - メタデータ: 年・場所・人物・タグ。同じ時代・同じ場所のつながりを機械的に求めたり、年表や地図の表示に使う
  - 画像とそのライセンス情報
- 出題形式は問題の内容に合わせて選ぶ。生成時のルールとして内容と形式の対応を定める（ADR-0008）
- 生成時は生成とは別の検証パスで事実確認を行う。アプリには「この問題おかしい」報告ボタンを設ける
- 問題の追加は、生成用の Claude Code スキル等で「テーマ X に N 問追加」を実行し、デプロイする

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **事前生成（採用）** | API キー不要・無料・品質レビュー可能・オフラインで動く | 問題追加に生成とデプロイの手間がかかる |
| 実行時生成（サーバー経由） | 問題が無限に作れる | サーバー・キー管理・API 費用・不正利用対策が必要。誤りが検証されずに出る |
| BYOK（利用者が自分の API キーを入力） | サーバー不要 | 一般の利用者には導入の敷居が高い |

## 結果

- 良い影響: 運用コストがほぼゼロ。公開前に内容をレビューでき、ハルシネーションを抑えられる
- 悪い影響: 問題数は生成した分だけ。追加は手動、または定期実行（ADR-0006）に依存する
- リスク: 年号・作者と作品の対応・画像と問題の対応などの誤り → 検証パス、報告ボタン、正答率の異常検知（ADR-0006）で対処する
